# 技术说明

本文汇总 MaaUpdaterBat 所依赖的**官方更新机制**、**实测数据**与**关键约定**，供维护、
排查与二次开发参考。使用方式见 [`../ghupdate/README.md`](../ghupdate/README.md)，
项目总体介绍见 [`../README.md`](../README.md)。

> 文中的实测数据取自 **2026-10-15** 的一次性测量，仅代表当时当地的网络环境与程序
> 版本，不构成对未来的保证。凡涉及第三方服务的可用性，均可能随时变化。

---

## 一、背景：网络环境实测

本工具的存在前提是**本机到 GitHub 的文件分发通道不可用**。该结论由以下测量得出。

### 1.1 通道状态

| 通道 | 实测结果 | 判定 |
|---|---|---|
| SSH `github.com:22` 认证 | `Hi important2sys! You've successfully authenticated` | 正常 |
| SSH 完整握手（`:22` / `ssh.github.com:443`） | 3.41 s / 4.45 s | 偏慢（跨境 RTT 放大） |
| `git ls-remote` | 4.5 – 5.9 s | 可用 |
| **HTTPS 直连 `github.com:443`** | **10 s 超时** | 不可达 |
| HTTPS 直连 `raw.githubusercontent.com` | 20 s 超时 | 不可达 |
| HTTPS 直连 `codeload.github.com:443` | 301，可达 | 可达 |
| **下载 `release-assets.githubusercontent.com`** | **63 KB/s** | 被限速 |
| **下载 `codeload.github.com`** | **26 KB/s** | 被限速 |

**关键区分**：代码传输（SSH）与文件分发（HTTPS release 附件 / 压缩包）是两条不同
的通道。前者正常，后者被限速并在长连接时被中途 RST。二者不可混为一谈。

DNS、ICMP 均正常（`github.com → 20.205.243.166`，ping 平均 130 ms、0% 丢包）；
hosts 未被改写；本机无代理进程。

### 1.2 官方下载源已失效

拉取 `api.maa.plus/MaaAssistantArknights/api/version/stable.json` 解析后：

- 文件中共 **67 个 `mirrors` 数组，全部为空 `[]`**
- 脚本 `Python/asst/updater.py` 中原本存在的三个官方 CDN —— `s3.maa-org.net`、
  `agent.imgg.dev`、`maa.r2.imgg.dev` —— 在元数据中**出现次数为 0**，且三个域名
  实测均不可达

因此程序本体更新只剩 GitHub 一条路，而这正是被限速的那条。

## 二、三条更新链路的官方机制

`ghupdate` 覆盖三条相互独立的链路。三者的版本来源、包体量与校验手段各不相同。

### 2.1 链路①：MAA 程序本体

| 环节 | 机制 |
|---|---|
| 查版本 | `api.maa.plus/.../version/summary.json` → `stable.json`，含 67 个资产 |
| 资产命名 | 全量 `MAA-v{版本}-win-x64.zip`；增量 `MAAComponent-OTA-{起点}_{目标}-win-x64.zip` |
| 版本探测 | 首选读 `config/gui.new.json` 的 `Update.UpdatePackage`，正则 `OTA-(.+)_(.+)-win-x64\.zip` 取起点；以 `MAA.exe` 的 PE FileVersion 交叉校验 |
| 官方摘要 | 全部资产提供 SHA256 `digest`（经 `api.github.com/.../releases/tags/{tag}` 获取） |

增量包对**从 v6.16.0 起、直到目标版本的每一个起点版本**都有对应资产。

**官方更新器 `MAA.Updater.exe` 的行为**（由二进制字符串与日志还原）：它是独立的
C++ 进程，由 `MAA.exe` 以 `--mutex-name` 启动，随后等待父进程退出（超时则强杀）、
取互斥锁、解压到 `NewVersionExtract\`、逐文件原子替换、按清单删除旧版本多余文件、
失败则从备份回滚、最后重启程序（`--skip-startup-auto-run`）。

本工具**不复刻**这一私有协议（update plan 未公开），而是自行完成「下载 → 校验 →
解压覆盖 → 应用 removelist → 版本复核」。代价是不具备「父进程退出后自动替换」
的能力，因此要求先手动关闭程序。

`MaaCore.dll` 没有 Win32 版本资源（FileVersion 为空），不能用于版本探测。

### 2.2 链路②：MAA 资源

资源指 MAA 安装目录下 `resource\` 内的关卡坐标、模板图、`stages.json` 等数据，
与「游戏资源」无关。

| 环节 | 机制 |
|---|---|
| 查版本 | `mirrorchyan.com/api/resources/MaaResource/latest`，**无需 CDK** |
| 下载 | `github.com/MaaAssistantArknights/MaaResource/archive/refs/heads/main.zip` |
| 本机版本 | `resource/version.json` 的 `last_updated` |
| 官方摘要 | **无**。GitHub 对分支归档（`archive/refs/heads/*`）不提供 digest |
| 校验 | 语义校验 + CRC32，见第四节 |
| removelist | **无**，因此不做 prune（无法判断哪些本地文件该删） |

版本判定为**字符串直接比对**：mirrorchyan 的 `version_name`（如
`2026-10-14 15:45:24.000`）与本机 `resource/version.json` 的 `last_updated` 是同一
字符串。

资源包体量仅 13.5 MB，这解释了它在直连限速下「一直还能忍」的原因 —— 同样被限速，
14 MB 可以熬过去，284 MB 必然断链。

### 2.3 链路③：MaaEnd 程序本体

| 环节 | 机制 |
|---|---|
| 查版本 | `api.github.com/repos/MaaEnd/MaaEnd/releases/latest` 的 `tag_name` |
| 下载 | `MaaEnd-win-x86_64-{tag}.zip` |
| 本机版本 | `interface.json` 的 `version` 字段（**`MaaEnd.exe` 的 FileVersion 是 2.7.0，不可用**） |
| 官方摘要 | 有（资产 `digest`） |
| 前置 | 依赖 MaaFramework（`maafw/` 目录随包更新），最低版本要求由程序自身校验 |

MaaEnd 另有 `cache\*.downloading` 残骸机制：下载中断会留下
`{资产名}.{序号}.downloading` 文件，本工具在更新前会清理（可用 `--keep-residue` 保留）。

## 三、端点可达性与速度（2026-10-15 实测）

| 端点 | 结果 | 用途 |
|---|---|---|
| `api.maa.plus/.../version/summary.json` | 200，0.23 s | MAA 查版本 |
| `api.github.com/repos/...` | 200，1.79 s | MaaEnd 查版本、取官方 SHA256 |
| `mirrorchyan.com/api/...` | 200，0.29 s | MAA 资源查版本 |
| `end.maafw.com` | 200，0.24 s | MaaEnd 公告 |
| `codeload.github.com/.../zip/refs/heads/main`（直连，资源包） | 200，**20.9 KB/s** | 资源下载兜底 |
| `ghfast.top/https://github.com/...` | 200，**669 KB/s – 2.24 MB/s** | 下载主通道 |
| `ghfast.top/https://api.github.com/...` | **403** | 不可用 —— 镜像只代理 `github.com`，代理不了 API |

**镜像测速（对真实 release 文件）**：13 个常见 GitHub 加速镜像中，`ghfast.top` 是唯一
可用者；其余为 403 / 超时 / DNS 失败 / 限流。第三方镜像生态极不稳定，不可作为长期依赖。

镜像的一个便利特性：`ghfast.top` **自行处理** `github.com → release-assets.
githubusercontent.com` 的 302 跳转，因此只需经它处理 `github.com` 一个域名。

## 四、校验依据

三条链路的校验能力**并不相同**，这是理解本项目安全边界的关键。

### 4.1 程序本体：官方 SHA256

MAA 与 MaaEnd 的发布资产均由 GitHub 提供官方 `digest`，格式为 `sha256:<hex>`。
下载完成后逐字符比对，**不符立即中止，不落地任何文件**。

实测样例：

| 包 | 官方 SHA256 |
|---|---|
| `MAA-v6.19.0-win-x64.zip` | `51463ce5cbcb37b85c1e3a5bd3fb11d7a33f4607a2c65578b96297366629b73a` |
| `MAAComponent-OTA-v6.18.0_v6.19.0-win-x64.zip` | `0dd03078e71ef6f2e55a1114c470fe36933e59d64a82ac515e68d717a4d4fed5` |
| `MaaEnd-win-x86_64-v2.32.0.zip` | `f335b1c260f8719bf4e527519ee64026c8c2aeb80f462aac58abbb5d2a671328` |

### 4.2 资源包：语义校验 + CRC32

资源包没有官方摘要，因此采用两级校验，均不依赖哈希：

**第一级 · 包内版本语义比对。** 解压**之前**，从 zip 中读出 `resource/version.json`
的 `last_updated`，必须**严格等于** mirrorchyan 报出的 `version_name`。

```
mirrorchyan 报出      : "2026-10-14 15:45:24.000"
包内 version.json 的  : "2026-10-14 15:45:24.000"   ← 必须一致
```

这一条能挡住：空包、错分支、截断的 zip、镜像返回的错误页、被替换的旧版本。

**第二级 · zipfile 自带的 CRC32。** `zipfile.testzip()` 在解压每个条目时自动校验
CRC32，损坏即抛 `BadZipFile`。这不是防篡改，只能防传输损坏。

### 4.3 ETag 不可用作校验和（已证伪）

GitHub archive 的 ETag 长度与 SHA256 相同，极易误用：

```
ETag            : cc547535f3208d806063f7719896e96a4376f55b17f5a376601e0b15ed5d0dfc
实际 SHA256     : c95911ab65674e083704b4b3bbd9fa7695c7ffa3d7ff1ad0fa565c594d53cd7c
匹配            : False
```

ETag 对同一 commit 稳定（镜像与直连返回一致），可用作「内容是否变化」的标识，但
**不能验证完整性**。

### 4.4 各链路校验能力对照

| 链路 | 官方摘要 | 镜像篡改能否被发现 |
|---|---|---|
| MAA 程序本体 | 有 | 能 —— 摘要不符拒绝写入 |
| MaaEnd 程序本体 | 有 | 能 |
| MAA 资源 | 无 | 有限 —— 语义校验挡不住同时改写版本文件与内容的镜像站 |

详见 [`../安全提醒与免责声明.md`](../安全提醒与免责声明.md)。

### 5.3 用户数据保护

三个程序本体包**均不含** `config/`、`cache/`、`debug/`、`data/` 等用户目录，因此直接
解压覆盖不会破坏设置与登录状态。

资源包亦**不含** `custom_infrast/`、`config/`、`copilot/`、`onnx/`、`PaddleOCR/`、
`minitouch/`、`platform_diff/`。本机 `resource/` 有 20 个顶层条目、约 288 MB，而包内
仅覆盖其中 4 个目录 + 7 个根文件。`--prune` 也会跳过 `config/cache/debug/data/
_MaaResource`。

### 5.4 增量写入

资源更新按**逐文件 `size` + CRC32** 比对，仅写入内容不同的文件。实测本机 5,311 个
文件与包内**逐字节一致**，判定结果 5311 相同 / 0 需写入，零误判。

因此日常更新的写入量与备份量为「实际变化量」（几 MB 量级），而非 99 MB 全量。

## 六、目录与路径约定

### 6.1 配置文件

位置按序探测，先命中先用：

1. `--config PATH`
2. 环境变量 `GHUPDATE_CONFIG`
3. `ghupdate\config.json`（默认，便携）
4. 均无 → 内置默认值

优先级：**CLI 参数 > 环境变量 > config.json > 内置默认**。

`config.json` 不入版本库（含个人安装路径），模板为 `config.example.json`。写入采用
原子替换（先写 `.tmp` 再 `os.replace`）。

### 6.2 安装目录解析

设计契约为：**要么使用指定目录，要么明确报错 —— 绝不静默回退到其他目录。**

| 级别 | 来源 | 类别 |
|---|---|---|
| 1 | `--install PATH` | 显式 |
| 2 | `GHUPDATE_INSTALL_MAA` / `GHUPDATE_INSTALL_MAAEND` | 显式 |
| 3 | `config.json` → `install.*.path` | 隐式默认值 |
| 4 | 交互式询问 | — |

显式来源校验失败时**立即报错退出**，不会退回使用 `config.json` 中保存的目录 —— 否则
可能出现「以为在更新 A、实际改了 B」的情况。隐式来源失效时允许被交互输入覆盖。

路径会被自动规范化：去引号与首尾空白、展开环境变量与 `~`、正斜杠转本地分隔符、
去尾部反斜杠、直接填 `*.exe` 时取所在目录。

一层子目录容错（`locate.parent_probe`，默认开）仅在指定目录的**直接子目录**中查找
唯一候选并征求确认，不是全盘扫描。非交互模式下不采用任何候选。

### 6.3 运行期目录

| 路径 | 内容 | 是否入库 |
|---|---|---|
| `ghupdate\config.json` | 安装目录、镜像偏好、行为开关 | 否 |
| `ghupdate\_cache\` | 下载包与 `.part` 断点残片（实测约 315 MB） | 否 |
| `ghupdate\_backup\<程序>-<时间戳>\` | 更新前备份，回滚用（实测约 372 MB） | 否 |
| `ghupdate\gui-error.log` | 图形界面未捕获异常 | 否 |

## 七、运行环境与解释器

### 7.1 硬约束：Windows

`update_maa.py` 通过 `ctypes.WinDLL("version")` 读取 PE 文件版本资源；`_common.py`
通过 `tasklist` 判断进程状态；`gui\theme.py` 通过 `shcore` / `user32` 做 DPI 感知。
`.bat`、`certutil`、`taskkill`、`netstat` 亦均为 Windows 专有。全部 `.bat` 使用
`%~dp0` 自定位，全部 `.py` 使用 `__file__` 推导脚本目录，无绝对路径假设。

### 7.2 两套解释器并存

| 入口 | 探测条件 | 本机命中 | tkinter |
|---|---|---|---|
| `update-all.bat`（命令行） | `sys.version_info >= (3, 8)` | managed 3.13.x | **无** |
| `ghupdate-gui.bat`（图形界面） | `>= (3, 8)` **且** `import tkinter` | 系统 Python 3.14.6（Tk 8.6） | 有 |

managed Python 未随附 Tcl/Tk，`import tkinter` 直接 `ModuleNotFoundError`。tkinter 随
解释器编译，无法通过 `pip` 补装。因此命令行用 managed（启动快），图形界面用系统
Python；两者运行**同一份源码、同一个 `config.json`**。跨解释器兼容性已实测（3.12 /
3.13 / 3.14 均编译通过，`--show-config` 与 `--check` 输出正常）。

已知不具备 Tcl/Tk 的常见分发：Microsoft Store 版 Python、部分 conda / miniforge 的
`python-minimal`、未启用 `_tkinter` 的自编译构建。

### 7.3 字体

界面字体使用 `Microsoft YaHei UI`，日志区使用等宽 `Consolas`。`SimSun` / `SimHei`
在本机缺失，不作为候选。

### 7.4 第三方依赖

**零第三方依赖**，全部使用 Python 标准库（`urllib` / `zipfile` / `ctypes` / `tkinter`
等）。这既是约束（构建环境 PyPI 不可达）也是优点 —— 拷贝到任何具备 Python 的 Windows
机器即可运行。

## 八、迁移到其他设备

代码本体完全可移植，设备状态不可移植。

| 维度 | 结论 |
|---|---|
| 代码 | 全部相对定位，无绝对路径假设 |
| 配置 | `config.json` 不入库，首次运行会询问安装目录，有完整兜底 |
| 缓存与备份 | 自动重建 |
| 环境 | 需 Windows + Python；图形界面另需带 tkinter 的解释器 |
| 网络 | **不可迁移** —— 端点可用性与限速情况属当前网络特征 |

模块内不含硬编码的设备路径。若新设备直连 GitHub 畅通，则本工具没有使用必要。
