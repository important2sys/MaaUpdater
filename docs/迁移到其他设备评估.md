# MaaUpdaterBat 迁移到其他设备 —— 影响评估与操作清单

> 评估日期：2026-10-15
> 评估对象：`D:\RRL\MaaUpdaterBat`（HEAD `d83c796`，34 个跟踪文件，`.git` 445 KB）
> 触发问题：「迁移到其他设备使用会有什么问题吗」

---

## 结论摘要

**代码本体完全可移植，但设备状态不可移植。**

| 维度 | 结论 |
|---|---|
| 代码 | ✅ 全部用 `%~dp0` / `__file__` 定位，无相对路径假设，零第三方依赖 |
| 配置 | ⚠️ `config.json` 在 `.gitignore` 里，不会跟着走 —— 有报错与交互兜底，风险低 |
| 证书 | ⚠️ `ghproxy/certs/` 同样不入库，**且本机现在也已不存在** —— ghproxy 需要重建才能用 |
| 硬编码 | ❌ **2 处必须手改**（`run-maa.bat` / `run-maaend.bat` 里的 exe 绝对路径） |
| 环境 | ⚠️ 需要 Windows + Python；图形界面另需带 tkinter 的解释器 |
| 网络 | ❌ **不可迁移**：`ghfast.top` 的可用性、直连被阻断都是本机实测结论 |

一句话：**把文件夹拷过去、改 2 行路径、重跑一次 `gen-certs.bat`，就能用**。但「能不能加速」完全是新设备网络环境的事，这里给不出保证。

## 一、跟着走的部分（无需处理）

- **全部 34 个跟踪文件**：`ghupdate\`（含 `core\`、`gui\`）、`ghproxy\`、`docs\`、两份 README、`.gitignore`
- **定位方式**：所有 `.bat` 用 `%~dp0` 取自身目录，所有 `.py` 用 `__file__` 推脚本目录；`core\config.py` 的 `script_dir()` 也是这么来的 —— 没有任何「假设在 D 盘」的代码
- **依赖**：零第三方包，只用 Python 标准库（`urllib` / `zipfile` / `ctypes` / `tkinter`）
- **体积**：`.git` 445 KB，代码 2000 余行 —— 用 U 盘拷、压缩包传、或者 git clone 都无所谓

`ghupdate` 与 `ghproxy` 两个子系统之间**没有交叉依赖**，可以只迁其中一个。

## 二、不会跟着走的部分（已被 `.gitignore` 排除）

| 项 | 内容 | 迁移后 | 严重度 |
|---|---|---|---|
| `ghupdate\config.json` | 两个安装目录的绝对路径（`D:\RL\MAA-v6.9.5-win-x64`、`D:\RL\MaaEnd-win-x86_64-v2.23.0`）、镜像偏好、代理 | 不存在 → 首次运行会**问你目录**，输入合法即写回 | 低（有完整兜底） |
| `ghproxy\certs\` | 私有 CA（`ghmirror-ca.crt` / `.key`）、`github.com` 叶证书、CA 指纹 | 不存在 → `ghproxy-ctl.bat start` 直接报 `missing certs\ghmirror-ca.crt` | **中**（需重跑 `gen-certs.bat`） |
| `ghupdate\_cache\` | 下载缓存、断点续传残片 | 自动重建 | 无 |
| `ghupdate\_backup\` | 更新前备份 | 自动重建 | 无 |
| `gui-error.log` | GUI 崩溃日志 | 自动重建 | 无 |

**一个需要更正的事实**：`ghproxy\README.md` 第五节写着「生成的 `certs\` 已随本套件提供」—— 这句话**现在不成立**。`certs/` 既被 `.gitignore` 排除，本机也已不存在（已清理）。新设备上**必然**需要先跑一次：

```bat
cd ghproxy
gen-certs.bat          :: 需要 openssl（Git for Windows 自带）
```

生成的新 CA 会得到**新的指纹**，与旧设备不同 —— 这不影响使用（`ca_installed.flag` 也是本机状态，不会跟着走），但如果你在多台设备间对比日志就会对不上。

## 三、硬编码路径清单

按「是否真的会坏」排序：

### 3.1 必须改（不改就用不了）

| 文件 | 行 | 内容 | 后果 |

| `ghproxy\run-maa.bat` | 13 | `set "APP=D:\RL\MAA-v6.9.5-win-x64\MAA.exe"` | 新设备路径不同 → `[ERROR] not found` 后 `pause` 退出 |

这两个脚本是 ghproxy（方案 A）**唯一的启动入口**，没有兜底、没有探测。改法就是在第 13 行填新设备上的实际路径。

### 3.2 有兜底，属整洁问题

| 文件 | 行 | 内容 | 现有兜底 |

| `ghproxy\ghproxy-ctl.bat` | 43 | `C:\Users\33974\.workbuddy\binaries\python\versions\3.13.12\python.exe` | 前面有 `py` → `python` → `%LOCALAPPDATA%\Programs\Python\Python313|314` 四级回落，**只在全部落空时才用到这一行**，且它在新设备上必然落空 |

| 文件 | 行 | 内容 |
|---|---|---|

这只是「你可能想这么写」的示意，不是程序逻辑。但新设备上看到这个提示会困惑（「它怎么知道我有 D:\RL？」），建议改成中性占位符。

## 四、环境前提（新设备要具备）

### 4.1 必须：Windows

不是「推荐」，是**硬约束**：

- `ghupdate\update_maa.py` 读版本靠 `ctypes.WinDLL("version")` → PE 文件版本资源，纯 Windows API
- `_common.py` 判断程序是否在运行靠 `tasklist`；`IS_WINDOWS = (os.name == "nt")`
- `gui\theme.py` 的 DPI 感知走 `shcore / user32`
- 所有 `.bat`、`certutil`、`taskkill`、`netstat`
- MAA / MaaEnd 的更新资产名带平台后缀（这里用的是 `win-x64`）

在 Linux / macOS 上，`core\` 的纯逻辑部分（config / locate / mirror）理论能跑，但整体不可用。

### 4.2 必须：Python

| 用途 | 要求 | 谁来找 |
|---|---|---|
| 命令行 | Python 3.8+ | `update-all.bat` 的 `:find_py`：WorkBuddy 托管 → `%LOCALAPPDATA%\Programs\Python\Python312/313/314` → `where python` |
| 图形界面 | **带 tkinter** 的 Python | `ghupdate-gui.bat`：`%MAAUPD_PYTHON%` → `%LOCALAPPDATA%\Programs\Python\Python3*` → `%APPDATA%\uv\python\cpython-*` → `where pythonw`，逐个验证 `import tkinter` |

**GUI 这条是迁移时最容易踩的**：tkinter 随解释器编译进来，**装不上也补不了**。以下 Python 分发通常不带 Tcl/Tk，会导致界面起不来：

- Microsoft Store 版 Python
- 部分 conda / miniforge 的 `python-minimal`
- 自己编译时没带 `_tkinter` 的构建

好在 `ghupdate-gui.bat` 探测全部失败时会打印**试过哪些路径 + 怎么修**（含 `setx MAAUPD_PYTHON` 示例），并提示「命令行界面不需要 tkinter，`update-all.bat` 仍然可用」—— 不会给你一个静默的黑屏。

### 4.3 条件性需要

| 依赖 | 什么时候需要 | 说明 |
|---|---|---|
| `openssl` | 只在重跑 `gen-certs.bat` 时 | Git for Windows 自带；`gen-certs.bat` 会依次找 `%ProgramFiles%\Git\usr\bin`、`mingw64\bin`、`%ProgramFiles(x86)%`、`where openssl` |
| SSH 私钥 | 只在要 `git push` 时 | 远端是 `git@github.com:important2sys/MaaUpdaterBat.git`，走 SSH。新设备需要重新生成 key 并加到 GitHub，或从旧设备拷贝 `~/.ssh` |

**只需要用、不需要改的话，`openssl` 和 SSH 都可以不管** —— 直接从旧设备拷整个文件夹最省事。

## 五、网络环境：最不可控的一项

### 5.1 `ghfast.top` 没有可迁移性

当前 `config.json` 里配的镜像 `https://ghfast.top/`，是 **2026-10-15 在本机、在本网络下**实测 13 个镜像后**唯一可用**的一个（其余 12 个：403 / 超时 / DNS 失败）。它是个第三方公益镜像，**随时可能限速或下线**。

换到别的 ISP、别的地区、别的时段，结果可能完全不同：

- 可能 `ghfast.top` 也不通 → 回落到直连（本机 63 KB/s，新设备可能更快也可能直接失败）
- 也可能本机测试失败的某个镜像在新环境下反而好用

**好消息**：这一项是**可配置且有兜底**的，不用改代码：

```bat
:: 临时换镜像（可重复传，按顺序尝试）
update-all.bat maa --mirror https://镜像地址/

:: 或写进配置 / 图形界面的设置页
```

`fallback_direct: true` 保证镜像全失败后还会试 GitHub 直连。`ghupdate` 的下载器本身支持「多 URL 依次尝试 + 断点续传 + 重试」。

### 5.2 「直连 GitHub 被阻断」是网络特征，不是设备特征

本机的实测结论（`github.com:443` 直连 20 秒超时、release 分发通道被限速到 26–63 KB/s 且长连接被 RST）**只对当前网络成立**。这正是整套工具存在的理由。如果新设备直连 GitHub 本来就很快，那这套东西**根本不需要用**。

### 5.3 一个鸡生蛋问题

远端仓库是 GitHub 上的私有仓库。**要用这套工具，得先能访问 GitHub**。当前网络直连被阻断，所以在新设备上 clone 时同样会遇到这个问题。绕过的办法：

1. 直接从旧设备**拷贝整个文件夹**（最省事，`config.json` 和 `certs/` 也能一起带过去 —— 但要删掉 `config.json` 里的重路径或改掉它）
2. 用 `ghfast.top` 代理 clone：`git clone https://ghfast.top/https://github.com/important2sys/MaaUpdaterBat.git`
3. 走 SSH（本机 SSH 通道是通的，只是握手 3.4 秒）

### 5.4 ghproxy 的 MITM 前提是「程序特性」，与设备无关

方案 A（本地代理拦截 `github.com`）能成立，是因为 MAA（.NET / schannel）与 MaaEnd（rustls + `rustls-platform-verifier`）**都信任 Windows 证书库**。这是**程序构建方式**决定的，换设备不变 —— 前提是新设备上装的是**同类的构建**。

如果新设备上换了个 TLS 后端不同的版本（例如改用内置 `webpki-roots` 而不是系统库），MITM 拦截就会因证书不受信任而失败。届时改用方案 B（`ghupdate` 直连镜像）即可，不需要这套代理。

## 六、迁移操作清单

### Step 0 · 迁前（在旧设备上）

- [ ] 确认仓库是最新的：`git status` 干净、`git pull`
- [ ] 决定要不要带 `config.json`：带就记住里面是旧路径，迁后要改；不带就等首次运行重新指定
- [ ] 记下两个安装目录的新位置（如果 MAA / MaaEnd 也要一起搬）

### Step 1 · 取代码（新设备）

三选一：

```bat
:: A. 直接拷贝文件夹（推荐，最省事，不依赖网络）
::    把 D:\RRL\MaaUpdaterBat 整个复制过去

:: B. 经镜像 clone
git clone https://ghfast.top/https://github.com/important2sys/MaaUpdaterBat.git

:: C. SSH clone（需要先配好 key）
git clone git@github.com:important2sys/MaaUpdaterBat.git
```

### Step 2 · 改硬编码（**必做**）

```bat
:: ghproxy\run-maa.bat 第 13 行
set "APP=<新设备上的 MAA.exe 完整路径>"

:: ghproxy\run-maaend.bat 第 13 行
set "APP=<新设备上的 MaaEnd.exe 完整路径>"
```

不改这两个文件，`ghproxy` 整套就用不了。`ghupdate` 不受影响（它靠 `config.json` + 交互询问）。

### Step 3 · 验证命令行（不用管 ghproxy）

```bat
cd ghupdate
update-all.bat                     :: 交互菜单
update-all.bat check               :: 干跑，不下载
update-all.bat --install "新路径\MAA-xxx"    :: 指定目录
```

首次运行会问安装目录，**输入合法就记住**，之后不用再输。

### Step 4 · 验证图形界面

```bat
cd ghupdate
ghupdate-gui-debug.bat             :: 先跑 debug 版，能看见报错
```

能看到窗口、两张卡片显示正确的当前版本，就说明 tkinter 那条链路通了。确认无误后日常用 `ghupdate-gui.bat`（无黑窗）。

### Step 5 · 重建证书（只有要 ghproxy 时）

```bat
cd ghproxy
gen-certs.bat                      :: 需要 openssl
ghproxy-ctl.bat status              :: 应显示 CA 未安装、端口关闭
```

### Step 6 · 跑一次真更新

先 `--check` 干跑，再实际更新一次小体积的目标（MaaEnd 包比 MAA 小得多）验证全流程。

## 七、建议：把硬编码清理掉

当前 3.1 的两处是**唯一会让迁移直接失败**的硬编码。按下面的思路改，迁移成本能从「改 2 个文件」降到「什么都不用改」：

| 位置 | 改法 |
|---|---|
| `run-maa.bat:13` / `run-maaend.bat:13` | 改为「若已设 `%MAA_EXE%` 就用它，否则读 `ghupdate\config.json` 里记的安装目录」，与 `ghupdate` 共用同一份配置 |
| `ghproxy-ctl.bat:43` | 直接删掉这行（前面四级回落已足够） |
| `update-all.bat:39-41` | 删掉 WorkBuddy 托管路径（私有环境，不该入库） |
| `locate.py:31/38` | 示例命令改成 `--install "<MAA 安装目录>"` 中性写法 |
| `ghproxy\README.md` 第五节 | 更正「certs 已随套件提供」这句 —— 现在不成立 |

这几处都是小改动，风险低。做完之后「拷贝文件夹 → 能用」就真的成立了。

## 附：一句话回答

**能迁，成本不大**：代码零依赖、全相对定位，拷贝过去改 2 行路径（ghproxy 的两个 `run-*.bat`）即可；`ghupdate` 连路径都不用改，首次运行会问你。真正需要重新确认的是**新设备的网络**（`ghfast.top` 还能不能用、直连是不是也被阻断）和**新设备的 Python 带不带 tkinter** —— 这两项没有可迁移的答案，只能现场实测。
